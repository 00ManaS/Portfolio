Inventory Manager is a point-of-sale and stock system for pharmacies, groceries
and retail shops. One rule matters more than any other in a system like that:
**you can't sell what you don't have.** I thought I had it covered. Every
change to stock (sales, purchases, returns, manual adjustments) goes through a
single function, and that function runs inside a database transaction.

It turns out that isn't enough.

## The code

Here's the heart of it, trimmed down from the NestJS service:

```ts
async applyMovement(db: Db, input: MovementInput) {
  const { storeId, productId, quantity } = input; // quantity is signed

  const existing = await db.stockItem.findUnique({
    where: { storeId_productId: { storeId, productId } },
  });
  const current = existing?.quantity ?? 0;
  const next = current + quantity;

  if (next < 0) {
    throw new BadRequestException(`Insufficient stock (have ${current})`);
  }

  await db.stockItem.update({
    where: { storeId_productId: { storeId, productId } },
    data: { quantity: next },
  });
  // ...then write an audit row to stockMovement
}
```

A sale calls this inside `prisma.$transaction(...)`, so the receipt, the line
items, the stock change and the audit record either all happen or none do.
That part works. The problem is what a transaction _doesn't_ promise.

## Two cashiers, one shelf

Postgres runs transactions at **Read Committed** isolation by default. Each
statement sees data that was committed before it started, but nothing stops two
transactions from reading the same row at the same moment.

Say there are 5 boxes of paracetamol in stock and two cashiers each ring up 3:

| Step | Cashier A                 | Cashier B                 |
| ---- | ------------------------- | ------------------------- |
| 1    | reads quantity: **5**     |                           |
| 2    |                           | reads quantity: **5**     |
| 3    | 5 − 3 = 2, check passes   |                           |
| 4    |                           | 5 − 3 = 2, check passes   |
| 5    | writes **2**, commits     |                           |
| 6    |                           | writes **2**, commits     |

Both sales succeed. Six boxes are sold out of five, and the system says there
are still two on the shelf. That's two bugs at once: an **oversell**, and a
**lost update**, because B's write silently replaces A's.

The check in JavaScript is the issue. Between reading the number and writing
the new one, the number can change, and the code never finds out.

## Proving it

I didn't want to fix a bug I'd only reasoned about, so I replayed the exact
pattern against a real Postgres 16 database with two concurrent connections:

```txt
read → check → write (current code)
  stock before: 5, two cashiers each sell 3
  cashier 1: sold 3 (saw 5, wrote 2)
  cashier 2: sold 3 (saw 5, wrote 2)
  stock after: 2
```

Exactly as predicted.

## The fix: let the database do the check

Instead of reading, deciding and writing, ask Postgres to do all three in one
statement and tell you whether it worked:

```ts
const { count } = await db.stockItem.updateMany({
  where: { storeId, productId, quantity: { gte: amount } },
  data: { quantity: { decrement: amount } },
});

if (count === 0) {
  throw new BadRequestException("Insufficient stock");
}
```

This becomes a single `UPDATE ... SET quantity = quantity - $1 WHERE ... AND
quantity >= $1`. When two of these hit the same row, Postgres locks it: the
second one waits for the first to commit, then **re-checks the `WHERE`
condition against the new value**. With 2 boxes left, `2 >= 3` is false, no
row is updated, and the sale is rejected.

The same test against the fix:

```txt
atomic conditional update (fix)
  stock before: 5, two cashiers each sell 3
  cashier 1: sold 3 (left 2)
  cashier 2: rejected: insufficient stock
  stock after: 2
```

Adding stock (purchases, returns) never needs the check, so it becomes a plain
`increment`, which is atomic for the same reason:

```ts
await db.stockItem.upsert({
  where: { storeId_productId: { storeId, productId } },
  create: { businessId, storeId, productId, quantity: amount },
  update: { quantity: { increment: amount } },
});
```

## Why not the other options?

- **`SELECT ... FOR UPDATE`.** Locking the row before reading it also works,
  but Prisma doesn't expose it, so it means raw SQL in the middle of an
  otherwise typed service. The conditional update gets the same guarantee in
  one query.
- **Serializable isolation.** Postgres would detect the conflict and abort one
  transaction, but then every sale needs retry logic, and a busy shop hits it
  constantly.
- **A version column (optimistic locking).** Good for editing documents,
  where a conflict should be shown to a person. For stock there's nothing to
  show the cashier except "try again", which the conditional update already
  answers more precisely.

## What I took from it

A transaction makes a group of writes **all-or-nothing**. It doesn't make a
read-then-write sequence **safe from other transactions**. Those are different
guarantees, and it's easy to assume you have the second because you have the
first.

The habit I'm keeping: whenever code reads a value, decides something in
application code, and writes back, ask what happens if someone else writes in
between. Usually the answer is to move the decision into the write itself.

_The receipt number has the same shape (count the sales, add one), but a unique
constraint on it turns that race into a failed sale the cashier can retry,
rather than corrupted data._
